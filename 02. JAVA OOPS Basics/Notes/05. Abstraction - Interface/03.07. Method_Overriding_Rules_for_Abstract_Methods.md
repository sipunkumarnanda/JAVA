# 🌟 Introduction

In **Part 1**, we learned:

* ✅ What an Abstract Method is
* ✅ Why it has no body
* ✅ Why child classes must implement it
* ✅ How responsibility passes through inheritance

Now another important question arises.

> **When implementing an abstract method, can we write anything we want?**

The answer is **No.**

Java has strict rules for overriding abstract methods.

These rules ensure that **runtime polymorphism** works correctly.

---

# 🎯 Rule 1: The Method Name Must Be the Same

Parent

```java
abstract class BankAccount{

    abstract void deposit(double amount);

}
```

Correct Child

```java
class SavingsAccount extends BankAccount{

    @Override
    void deposit(double amount){

        System.out.println("Money Deposited");

    }

}
```

✔️ Correct

---

Incorrect

```java
class SavingsAccount extends BankAccount{

    void addMoney(double amount){

    }

}
```

❌ Compiler Error

Why?

Because

```text
deposit()

≠

addMoney()
```

The child has created a **new method** instead of overriding the parent's method.

---

# 🌟 Rule 2: Parameter List Must Be the Same

Parent

```java
abstract void deposit(double amount);
```

Correct

```java
void deposit(double amount){

}
```

✔️ Correct

---

Incorrect

```java
void deposit(){

}
```

❌ Compiler Error

---

Incorrect

```java
void deposit(int amount){

}
```

❌ Compiler Error

---

# 🤔 Why?

Method overriding means

> **Replacing the parent's implementation.**

If parameters change,

Java considers it a different method.

This is called

```text
Method Overloading

NOT

Method Overriding
```

# 🎯 Rule 3: Return Type Must Be Compatible

Parent

```java
abstract double calculateInterest();
```

Correct

```java
double calculateInterest(){

    return 500;

}
```

✔️ Correct

---

Incorrect

```java
String calculateInterest(){

    return "500";
}
```

❌ Compiler Error

# 🌟 Covariant Return Types

Sometimes,

the child can return a **subclass** of the parent's return type.

Example

Parent

```java
abstract class Animal{

}
```

```java
class Dog extends Animal{

}
```

Parent Method

```java
abstract Animal getAnimal();
```

Child

```java
Dog getAnimal(){

    return new Dog();

}
```

✔️ Valid

This is called

```text
Covariant Return Type
```

It allows the child to return a more specific type.

---

# 🎯 Rule 4: Access Modifier Cannot Become More Restrictive

Parent

```java
public abstract void deposit();
```

Correct

```java
public void deposit(){

}
```

✔️

---

Also Correct

```java
public final void deposit(){

}
```

⚠️ Wait!

This compiles **only if** the method is no longer abstract and you are implementing it here. However, making it `final` means **future subclasses cannot override it**.

---

Incorrect

```java
protected void deposit(){

}
```

❌ Compiler Error

---

Incorrect

```java
private void deposit(){

}
```

❌ Compiler Error

---

# 🤔 Why?

Imagine this.

Parent promises

```text
Everyone Can Access deposit()
```

If the child changes it to

```text
Only Family Members Can Access
```

the promise is broken.

Therefore,

visibility cannot be reduced.

---

# 📊 Access Modifier Table

| Parent    | Child     | Valid? |
| --------- | --------- | ------ |
| public    | public    | ✅      |
| protected | public    | ✅      |
| protected | protected | ✅      |
| public    | protected | ❌      |
| public    | private   | ❌      |

Rule:

> Child visibility can become **more accessible**, but never **less accessible**.

# 🎯 Rule 5: Checked Exceptions

This rule confuses many beginners.

Suppose

Parent

```java
abstract void readFile()
        throws IOException;
```

Child

```java
void readFile()
        throws IOException{

}
```

✔️ Correct

---

Child

```java
void readFile(){

}
```

✔️ Also Correct

The child can choose **not** to throw the checked exception.

---

Incorrect

```java
void readFile()
        throws Exception{

}
```

❌ Compiler Error

---

# 🤔 Why?

Because

```text
Exception
```

is **broader** than

```text
IOException
```

The child cannot promise to throw **more** checked exceptions than the parent declared.

---

# 📌 Easy Memory Trick

Child can throw

```text
Same Exception

OR

Smaller Exception

OR

No Exception
```

But **not a broader checked exception**.

---

# 🎯 Rule 6: @Override Annotation

Example

```java
class SavingsAccount
        extends BankAccount{

    @Override
    void deposit(double amount){

    }

}
```

The annotation

```java
@Override
```

is optional,

but highly recommended.

---

# 🤔 Why Use @Override?

Imagine you accidentally write

```java
void deposits(double amount){

}
```

Notice

```text
deposits()

≠

deposit()
```

Without

```java
@Override
```

Java thinks

> This is a completely new method.

No compiler error.

Bug enters your program.

---

With

```java
@Override
```

Compiler immediately reports

```text
Method Does Not Override
```

The mistake is caught early.

# 🎤 Interview Questions

### Q1. Must an overriding method have the same parameter list?

**Answer:**

Yes.

Changing the parameter list creates **method overloading**, not method overriding.

---

### Q2. Can an overriding method return a subclass?

**Answer:**

Yes.

This is called a **Covariant Return Type**.

---

### Q3. Can an overriding method reduce visibility?

**Answer:**

No.

The child method cannot have a more restrictive access modifier than the parent method.

---

### Q4. Is `@Override` mandatory?

**Answer:**

No.

It is optional, but strongly recommended because it allows the compiler to detect overriding mistakes.

# ⭐ Key Takeaways

✅ Overriding follows strict compiler rules.

✅ Method name and parameters must match exactly.

✅ Return type must be compatible.

✅ Visibility cannot be reduced.

✅ Child methods cannot throw broader checked exceptions.

✅ Always use `@Override` to catch mistakes early.

These rules ensure that **runtime polymorphism remains safe and predictable**.
